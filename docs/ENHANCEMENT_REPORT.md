# FinBiz 360 enhancement and validation report

Audit and implementation started 1 November 2026. The existing application was extended in place; no framework, database or authentication replacement was performed. This is a technically tested local release, not production or company UAT acceptance.

## Architecture and preservation

React/TypeScript/Vite remains the frontend, Node.js/Express ES modules the API, and built-in SQLite/WAL the database. Cookie sessions, scrypt passwords, server RBAC, CSRF, existing API endpoints and the single-organisation SLE model remain. All original pages and operations remain accessible. Source modules were added for financial enhancements, partial evidence allocations, restore operations and reusable UI controls.

Preserved workflows include sign-in/registration and empty onboarding; cash/mobile/bank transaction capture; immutable posted financial fields; receipts, expenses and independent payment approval; customer/supplier/account registration; invoices and partial receipts; CSV/XLSX mapping/preview/commit; exact-reference reconciliation and undo; audit history; reporting and CSV/PDF exports; reporting-period locks; separate synthetic demo; automatic 15-second refresh and protected evidence access. Existing `accounts.balance` remains filtered movement for API compatibility; `opening`, `movement` and `closing` supply explicit book-balance semantics.

The initial audit and implementation checklist is in [ENHANCEMENT_AUDIT.md](ENHANCEMENT_AUDIT.md). The supplied instructions are retained in [MASTER_ENHANCEMENT_REQUEST.md](MASTER_ENHANCEMENT_REQUEST.md). [REQUIREMENTS_BASELINE.md](REQUIREMENTS_BASELINE.md) preserves the earlier release inventory.

## Completed enhancements

- Audited user profile/role/status edits and session revocation; managers can explicitly delegate payment approval to active finance/admin users. Auditor roles remain read-only, and delegated staff cannot approve their own payments.
- Account names/providers/status, clearing purpose, explicit SLE, immutable opening balance/date, and separate opening/movement/closing values. Customer/supplier reference, email, address, search/status filtering, editing and histories.
- Private evidence upload/download with file-signature checks, manual evidence-review status, duplicate-reference warnings, richer transaction filters and allowlisted sorting, configurable active category references, submission/retry protection.
- Itemised and draft/issued/cancelled invoices, exact paid/outstanding amounts, payment histories and retained allocation corrections. Supplier bills, approved payment allocation/correction, and derived supplier balances.
- Independent control requests for adjustments/fees, document write-offs, reversals and period closures. Non-cash write-offs reduce document outstanding, preserve original amounts and never create receipts or label written-off amounts as paid.
- Configurable date/amount suggestion tolerances; rejected suggestions; independently approved balanced one-to-many/many-to-one/net-of-fee groups; exact minor-unit partial allocations with remaining amounts, overmatching protection, concurrent decision checks and undo.
- Central exceptions for unmatched records, duplicates, missing references, discrepancies, partial remainders and invalid statement rows. Investigation reasons and restricted manager dismissal retain source evidence. Financial resolution uses recorded corrections and approved matching.
- Shared reporting services with CSV/XLSX/PDF exports for transactions, income/expenses, cash flow, accounts/account statements, customer/supplier balances, invoices/bills, reconciliation, outstanding records and exceptions.
- Explained anomaly indicators and a sufficient-history-gated cash-flow baseline with held-out MAE and explicit assumptions/limitations. Real global search, header account/date controls, breadcrumbs, new operational destinations, skeleton loading and restrained turquoise surfaces.
- Consistent administrator backup export and a safe restore CLI that uses a new destination, validates integrity/counts/foreign keys and invalidates restored sessions.

## Defects and practical issues addressed

1. Missing user and master-record maintenance is now available with before/after audit details.
2. Channel filtering now uses the same account join in transaction counts, list data, dashboard data and report services. Unsupported/prototype sort keys cannot become SQL identifiers.
3. Unwarned repeated external references now return possible-duplicate warnings while legitimate separate records remain possible.
4. Incorrect receipt allocations can be corrected without deleting history. Supplier payment allocation has equivalent correction support.
5. Account movement was previously presented without configurable opening balances. Closing book balances and filtered movement are now separate and opening balances do not become income.
6. Invalid statement rows now retain raw input and downloadable validation reasons; row duplicates are warned about. Expanded workbook limits are checked before parsing.
7. Exact-only matching lacked reviewed non-exact/group/partial workflows. Added workflows revalidate remaining amounts, dates, approval state, reversals and period locks inside atomic decisions.
8. Per-row matching/exception lookups exceeded the synthetic query target (about 5.4 s and 7.0 s p95). Batched lookup maps reduce these costs; before/after evidence is retained.
9. Restored sessions and overwrite hazards are addressed by restore-to-new-file and session invalidation.
10. Authenticated API responses are not cacheable. Unknown-user password checking and malformed stored hashes are handled consistently.
11. Static header features now have real search/filter/navigation handlers. Obsolete UI statements about unavailable grouping/forecasting were replaced.
12. A revoked/expired client session now refreshes anonymous CSRF, clears cached financial context and returns to sign-in; wrong-password failures do not trigger logout. A focused client-protocol test verifies reauthentication.
13. A duplicate category-validator declaration was caught during preview startup and removed before final verification.

## Database changes and migration safety

- **v3:** additive account/contact/invoice metadata; category references; evidence and manual verification; allocation corrections; supplier bills/payments; matching policy/proposals/group links; exception reviews and supporting indexes.
- **v4:** explicit payment-approval delegation, with author/reason/time.
- **v5:** independent control requests, non-cash document write-offs and supplier-allocation correction history.
- **v6:** reviewed partial evidence allocations and indexed transaction/line lookup.

No migration deletes existing financial or audit rows or changes existing transaction values. Existing invoice inserts were changed to name their columns, so additional lifecycle fields do not break the old creation/seed paths. Migrations run when the application starts/restarts. They were tested against a populated historical v2 schema and on reopen; existing transactions, invoices, users and audit events compare unchanged. Company databases were not used for test/benchmark/preview seeding. The temporary preview used in-memory data and was stopped.

Schema rollback is not implemented as destructive down-migrations. Retain a verified pre-release backup and use the documented new-file restoration procedure with the appropriate release code if rollback is required.

## Security and financial-control evidence

Server permissions guard all new endpoints. A system administrator has no business approval authority unless a manager explicitly delegates payment approval. Manual/group/partial matching and control requests require a different manager. Cashier transaction/evidence access remains scoped; read-only reviewers cannot mutate. Posted financial/audit fields remain protected; correction and decision histories are retained. Monetary totals, allocations, write-offs, forecasts and report amounts use exact minor units/BigInt. Chart geometry alone uses numeric coordinates.

Uploads are bounded and served through authenticated attachment routes. No PIN, bank-password or CVV field exists. Statement originals and evidence are included in backups and must be protected as financial data. Prepared statements, explicit filters, sort allowlists, CSRF, session rotation/revocation and private cache headers remain in use. Production HTTPS, filesystem access controls, encryption/retention, MFA and monitoring are not supplied by a local preview and must not be claimed as deployed controls.

## UI/UX result and verification boundary

The existing teal reference dashboard is retained and extended with actual document obligations, unmatched records, real controls and appropriate empty states. The existing navigation destinations, small user profile area, Plus Jakarta Sans and readable rem-based sizes remain. Added management tables/forms use the existing modal, icon and input conventions. The earlier expanding blue card wipe has been replaced with restrained neutral/turquoise surfaces under the newer design brief.

Automated rendering verifies selected read-only/mutating control boundaries and displayed document balances. It is not browser interaction, visual pixel comparison, screen-reader certification or human usability testing. The browser host was unavailable; a native VS Code preview attempt timed out awaiting app access. These checks remain outstanding, rather than being reported as passed.

## Tests and performance

`npm test`: **44 passing automated tests**, including the original 21 cases, new financial/API tests, populated v2 migration preservation, safe backup restoration and rendered role-control checks. `npm run build` validates frontend types and bundles the application. `npm run format:check` validates source/document formatting. Final production build and formatting checks passed. `npm audit --json` and the production-only audit both reported zero known vulnerabilities; the recorded result is in DEPENDENCY_AUDIT.json. This does not certify application logic or production configuration.

`npm run benchmark` uses only synthetic in-memory SQLite data: 10,056 transactions, 2,000 statement lines, one process, warmed loopback requests, 20 samples per endpoint, concurrency one. The three-second p95 target is met in the recorded local test; this is not a production/disk/network/high-concurrency or browser-rendering guarantee. See [BENCHMARK.json](BENCHMARK.json) and [BENCHMARK_BEFORE_BATCHING.json](BENCHMARK_BEFORE_BATCHING.json).

## Outstanding requirements and recommendations

- **Blocked by External Dependency:** interactive cross-browser/mobile visual and accessibility acceptance, and actual company user sign-off. Native preview app access timed out; no participant feedback or pixel-match claim is invented.
- **Blocked by External Dependency:** organisation-approved production hosting/HTTPS, filesystem ACLs, encryption/key management, backup scheduling/storage/retention, monitoring and recovery objectives. No deployment was performed.
- **Partially Implemented:** operational restore is automated/tested; production recovery drills, encrypted schedules and agreed RPO/RTO remain an operator responsibility.
- **Not Implemented:** privileged MFA, provider payment feeds, FX/multi-currency conversion, negative opening snapshots, tax/credit-note accounting and a full double-entry ledger. A full ledger/FX migration is not required merely to preserve this SLE cash-management architecture.
- **Partially Implemented:** lifecycle and non-cash write-off decisions are retained; a dedicated credit-note/write-off reversal interface and configurable amount-threshold routing remain follow-up work requiring company policy. Existing explicit manager permissions and independent request routes are implemented.
- A local Git repository was initialised. Source changes were not committed or published; review and create the approved release checkpoint before deployment. No remote credentials or global Git identity were changed.
- SLE/two-decimal, one-organisation/single-instance constraints remain. Opening amounts are nonnegative, immutable snapshots; accepted movements can make a closing balance negative. Book balances are recorded balances, not independently verified provider balances.
- Document obligations have no financial-account attribution: issue-date filters apply, while account/channel filters do not purport to attribute an unpaid document to a payment account. Account closing balances include all accepted account activity; category/status filtering describes movement, not a different external bank balance.
- Partial matches remain explicit evidence allocations, not changes to cash amounts. Tolerance discrepancies are never silently rounded, written off or auto-confirmed. Record and approve the real fee/adjustment or allocate an explicitly reviewed partial amount.
- Forecasts are a recorded-data baseline with dated output, not financial advice or a guaranteed prediction. Assess missingness, stale records, seasonality and real held-out performance with the organisation before operational use.
